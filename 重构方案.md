# WitchDrawer Refactoring Review and Plan

## Scope and baseline

This is a targeted static review of the current `codex/basic-refactor` branch at version 1.4.4, not an exhaustive audit. The application uses native WPF, with Core, Native, and PluginSdk projects and separate App, Core, and Native test projects. Preserve existing product behavior and the file-safety rules in `AGENTS.md` throughout this work.

The Release build attempted during this review with the shared SDK failed because files in the App test project's output directory were in use by another process. The full test suite was not run, so the baseline is not yet verified. The default `dotnet` on PATH did not locate an SDK; use the shared executable explicitly.

The review found existing safeguards worth retaining: `DrawerService.InitializeAsync` runs initialization and recovery off the UI thread; pending file operations support recovery; and several file lists explicitly enable recycling virtualization. SQLite async methods can execute synchronously, so the existing background dispatch must not be removed merely because a method is asynchronous.

## Findings and priorities

1. **High: storage responsibilities are concentrated.** `src/WitchDrawer.Core/Storage/DrawerRepository.cs` contains schema initialization, migration and consistent-copy logic, box and item persistence, todo persistence, pending file operations, and shared connection helpers. This makes changes difficult to isolate and increases the chance of disturbing transaction or migration behavior. `SettingsRepository` already demonstrates one narrower boundary.
2. **High: file-operation orchestration is concentrated.** `src/WitchDrawer.Core/Services/DrawerService.cs` combines box and item operations, background dispatch, path repair, recovery, and a shared operation gate. Its recovery and compensation paths protect user data, so changes here require focused regression tests and small, separately reviewable steps. The existing `DrawerService.FileCommands.cs` already groups some operations.
3. **Medium: startup combines composition and lifecycle.** `src/WitchDrawer.App/App.xaml.cs` constructs services and view models while also handling startup ordering, event wiring, single-instance coordination, and shutdown. Extracting narrowly scoped wiring could make lifecycle behavior easier to inspect, but must preserve startup ordering, UI dispatch, error handling, and disposal.
4. **Medium: execution boundaries need explicit documentation before adjustment.** Core services use `Task.Run` at several entry points, and the repository performs potentially synchronous SQLite work. Measure and trace caller context and cancellation before changing scheduling. The presence of `Task.Run` or WPF `async void` event handlers alone is not evidence of a defect.
5. **Low: release guidance needs reconciliation.** The packaging script supports an installer by default, while the latest project instructions require portable-only delivery with `-SkipInstaller`. The root README says portable only, while inherited documentation still references upstream releases. Review documentation and script wording separately before making release changes; retain compatibility unless a change is approved.

## Proposed stages

### 1. Establish a repeatable baseline

- Use the shared .NET SDK under `D:\software\WindowsDev\dotnet` and the version selected by `global.json`.
- Run the existing Release build and tests; record failures before changing code. Review the existing startup and interaction measurements under `investigation/` and choose representative scenarios before performance-sensitive work.
- Record current behavior for database initialization, migration, pending-operation recovery, file conflict handling, and mapping-box references using existing tests. Add focused tests only where a proposed change exposes a meaningful gap.

### 2. Isolate todo persistence

- Separate todo-specific SQL and mapping from `DrawerRepository` into a narrowly scoped repository, using the existing settings repository as a reference. Keep the public facade and database connection, transaction, migration, ordering, and cancellation behavior unchanged.
- Run the existing todo, legacy migration, and repository tests, then the full solution build and tests. Do not change the database schema as part of this extraction.
- Acceptance: callers and persisted data behave identically, and todo changes can be reviewed without navigating unrelated item and recovery code.

### 3. Clarify file-operation and recovery boundaries

- Trace ownership of the shared gate, pending-operation journal, compensation, and recovery before extracting any code. Group one cohesive path at a time; keep the gate and transaction boundaries intact and keep file mutations in Core.
- Cover normal and mapping boxes, cross-volume moves, conflicts, missing original directories, cancellation, and interrupted operations with focused existing or new tests as applicable.
- Acceptance: recovery and file-safety outcomes match the baseline, with no file scanning, moves, or SQLite writes moved onto the UI thread.

### 4. Simplify application startup wiring

- Extract a small composition or lifecycle helper only where it removes a clear responsibility from `App.xaml.cs`. Preserve initialization and recovery ordering, single-instance behavior, refresh exception handling, UI-thread affinity, and shutdown ownership.
- Run App and Native tests and compare startup measurements with the baseline. Check list virtualization when affected views or templates change.
- Acceptance: startup, refresh, shutdown, and responsiveness remain equivalent; no new runtime dependency is introduced.

### 5. Align portable delivery documentation

- Reconcile current fork documentation with the portable-only instruction, and identify inherited upstream material explicitly. Do not publish a release or remove installer support without separate authorization.
- For each approved project change, increment the patch version, align relevant version information, run Release build and tests, and package via `tools\Publish-WitchDrawer.ps1 -Version X.Y.Z -SkipInstaller`. Inspect the complete ZIP and compare its SHA-256 sidecar with `Get-FileHash`.

## Review and delivery rules

- Treat each stage as a separate proposal and reviewable change; stop or adjust the plan if baseline tests or measurements reveal a risk.
- Avoid broad renames, dependency upgrades, schema changes, or abstractions introduced only to reduce file length. Any runtime dependency requires its cost rationale and prior confirmation.
- Preserve existing tests and add behavior-focused coverage for changed file moves, conflicts, deletion, persistence, and search. Do not claim improved performance without measurements.
- Obtain explicit confirmation before implementing a stage. Remote release publication requires separate authorization.
